## 4. Warrior skins

These are runtime material variants of the actual existing sprites, not newly redrawn characters. An AI-generated sapphire/gold brocade texture supplies the shared material pattern. The original source is retained in `production/cosmetics/brocade-source.png`.

The renderer applies palette/material changes to eligible fabric/armor pixels across base and Fate atlases. It retains source registration, frame selection, timing and alpha. Default rendering remains available. Krishna-specific cinematic sprites bypass the warrior material layer. Pixel tests verify unchanged silhouettes and unchanged upper head region for base skin poses; they do not constitute semantic verification of every facial pixel in every Fate frame.

## 5. Bow skins

The bows are baked into the existing warrior images. A separate material pass recolors eligible bow ornament pixels; it does not replace geometry or move the grip, arrow origin or string. All eight bow variants change visible pixels in idle, draw, release and damage poses. Bow gameplay regression tests pass.

## 6. Chariot customization

Four carriage material palettes apply to the existing lower carriage artwork. The rotating wheel uses the same material frame as the carriage. Existing horses, charioteers, Krishna, rescue animation registration and movement remain in place. The combined preview uses each warrior's established chariot type.

These are material finishes, not new chariot models or horse-armor sets.

## 7. EmoteController architecture

Six 1.6-second ceremonial **animated sigils** represent the emotes: bow salute, joined palms, crossed arrows, sunburst, lotus and oath banner. They are overlays, not full-body gesture animations.

Four slots support mouse/touch buttons and T followed by 1–4. Five-second cooldown, duplicate event suppression, opponent-hide preference and immediate battle cancellation are implemented. Managed online sessions allow only pre-round and post-round emotes. The server checks match state and equipped ownership. No emotes are inserted into combat inputs or rollback/referee state. Post-match status polling runs only while emotes are permitted and the page is visible.

## 8. Inventory and persistence

Permanent COSMETIC entitlements reuse `player_entitlements`. `cosmetic_loadouts` saves skin and bow per warrior, a chariot, four emotes and opponent-hide preference. Guest linking retains the same account inventory. Default buttons and empty emote slots are supported.

Purchases for locked warriors are rejected server-side. Local and Training access overrides do not grant permanent ownership. Fresh offline account restoration still requires reconnection, as in the existing account system.

## 9. Transaction security

The request accepts cosmetic ID and an idempotency request ID, plus the existing protocol field. The server determines price and validates availability, ownership, character prerequisite and balance.

One database batch inserts the receipt, debits the wallet and creates the entitlement. A failed entitlement insert rolls back the batch. Unique indices prevent duplicate permanent entitlements and duplicate account/request receipts. Already-owned purchases return inventory without another charge. Client retries retain their request ID and reconcile ownership after uncertain responses.

History records item/type, transaction/user ID, amount, before/after balance, time and source. Only Suvarna acquisition is implemented; other future source names are metadata.

## 10. Multiplayer synchronization

Match loadouts are derived from server-owned equipment and frozen with the selected warrior. Status and reconnect responses carry both seats' cosmetic IDs. Legacy room/relay responses also carry server-derived cosmetic IDs. Images remain local assets; projectile packets do not carry images or cosmetic data every frame.

Missing material falls back to original art without interrupting play. Managed-session emotes use separate server events. Legacy unmanaged room sessions do not have replicated emote support.

The fallback peer hello now includes counter/quiver metadata required by the existing receiver. Its older test fixture now supplies valid selected loadouts. The actual peer handshake and relay suites pass.

## 11. Mobile UI

Verified treasury and emote wheel in a 390 × 844 browser viewport, plus the desktop layout. The mobile header no longer overlaps tabs; selecting a preview brings its details into view. Controls use touch-sized targets. Emote controls are attached to pre/post-round screens and the existing command area.

This is browser viewport testing, not testing on a physical Android device.

## 12. Performance

The generated delivery texture is 181,535 bytes, reduced from approximately 4 MB; it is loaded lazily and sampled into a small pattern buffer. Material frames are capped at 320 pixels wide and a 96-entry cache. Shop previews run at about 12 frames/second, only while open, and skip offscreen cards. Existing animations and atlases are reused. The service worker includes new scripts and caches cosmetic art on demand.
